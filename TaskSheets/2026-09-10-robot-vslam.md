# カメラVSLAMロボット工作

- 日付: 2026-09-10
- ステータス: 進行中

## 目的

qwen-localのハードウェア工作入門として、カメラベースのVSLAM(Visual SLAM)で
自律的に動くロボットを作る。Lidarはコストが高いため単眼カメラを採用。
点群解析ソフトの仕事の知見を、将来的に自前のVO/マッピングロジックへ活かす方向で進める。

## 方針: 構成

- **カメラ+マイコン**: 当初Raspberry Piを予定していたが、品薄で価格が高騰・売り切れ
  (コンプリートキット、Pi Zero 2 W/WHとも売り切れ確認済み)していたため方針変更。
  ロボット側の役目は撮影・送信・モーター制御のみで重い処理をしないこと、また
  勉強を兼ねたい意向もあり、机の片付け装置と同じ**ESP32-CAM**に統一(確定)。
  Raspberry Piより大幅に安い(1台あたり約1,700円)が、PythonではなくArduino/C++で
  ファームウェアを書く必要がある。ESP32-CAMはカメラ用にGPIOの多くを占有するため、
  L298N制御用のGPIO確保(SDカード用ピンの転用など)はM1で要検討。
- **計算分担**: ロボット側(ESP32-CAM)は撮影とWi-Fi送信、モーター制御のみ。VSLAM本体は
  PC(RTX4070)側で実行する。Wi-Fi越しにフレームをPCへストリーミングし、PCから
  走行コマンドを返す構成。qwen-localで既に構築済みのOllamaネットワーク越し呼び出し
  (`OLLAMA_ORIGINS`)の土台を流用できる。

```
[ロボット本体]                      [PC: RTX4070]
ESP32-CAM                           Ollama (qwen2.5)
 + モータードライバ(L298N等)          + VSLAM処理 (pyslamなど)
 + TTモーター×2 + シャーシキット      + Qwenによる自然言語/意味理解層
     │  Wi-Fi (MJPEG/UDP映像ストリーム)
     │  Wi-Fi (走行コマンド受信)
     └──────────────────────────────┘
```

## マイルストーン

1. **M1 組み立て**: シャーシ+モーター+ESP32-CAMの配線、ESP32-CAM単体でモーター制御が動く

### M1配線計画(確定、2026-09-11 Freenove公式ピン配置図で検証済み)

Freenove ESP32-WROVER CAMはカメラ用に14本(GPIO4,5,18,19,21,22,23,25,26,27,34,35,36,39)、
フラッシュ用にGPIO6-11、ブートストラップ用にGPIO0,2,12(外部回路があると起動不安定になりうる)、
USBシリアル用にGPIO1,3が予約されている。安全に使えるのはGPIO13,14,15,32,33のみ。

| ESP32側 | L298N側 | 役割 |
|---|---|---|
| GPIO32 | IN1 | モーターA 方向制御 |
| GPIO33 | IN2 | モーターA 方向制御 |
| GPIO13 | IN3 | モーターB 方向制御 |
| GPIO14 | IN4 | モーターB 方向制御 |
| GND | GND | 共通グラウンド(必須) |
| 5V | 5V | ロジック電源(L298Nのオンボードレギュレータから) |

ENA/ENBはL298Nのジャンパを挿したまま(常時フル速度)にし、最初は方向制御のみ実装する。
PWMでの速度調整はGPIO15を使う拡張課題として後回し。
電源: 電池パック(+)→L298N「12V/VIN」、電池(−)→L298N GND。L298Nの5Vレギュレータ出力を
ESP32の5Vピンに接続し、電池1つで両方に給電する。
2. **M2 映像ストリーミング**: ESP32-CAMからPCへWi-Fi経由でカメラ映像をリアルタイム送信
3. **M3 VSLAM疎通**: PC側で受信映像に対し単眼VO/SLAM(`pyslam`など)を動かし、軌跡・自己位置を可視化
4. **M4 遠隔操縦**: PC→ESP32-CAMへ走行コマンドを送り、簡単なテレオペを実現
5. **M5(任意) Qwen連携**: 自然言語の指示をQwenで解釈してナビゲーション指令に変換、
   またはVSLAMで得た軌跡/マップに対する説明生成

## 派生: 点群化(確定)

単眼SLAMがそのまま出す特徴点はスパースすぎて「点群」として使うには不十分なため、
走行中に撮ったフレーム列を後段でSfM+MVS(COLMAPのような構造復元)にかけて
密な点群を再構成するステップを追加する方針に確定。カメラ機材の変更は不要で、
M3の出力(映像+推定カメラ姿勢)をそのまま入力にできる。点群解析の実務知見を
活かせる部分。

## 派生: 部材調達アシスタント機能

工作のたびに部材をWeb検索するのが面倒という話から、調達を助ける機能のアイデアが出た。
検討の結果:

- ローカルのQwen自体にはインターネットアクセス能力がない(Ollamaはテキスト生成のみ)ため、
  「検索/取得」は外部の検索API(Google Custom Search / Bing / Braveなど)が別途必要。
  Qwenの役割は取得した検索結果を渡して比較・要約・推薦させる部分。
- 購入(カート投入・決済)の自動化はしない方針。ECサイトのbot購入は規約違反になりやすく、
  お金が絡む取り消しにくい操作なので、最終的な「買う」ボタンは人間が押す設計にする。
- 当初は`frontend-tauri`に検索API連携の調達アシスタント機能を追加する案を検討したが、
  APIキー取得や実装コストに見合わないと判断し**見送り**。代わりに、部材が必要になった
  都度Claudeに直接Web検索させて候補URLを出してもらう運用にする(アプリ化しない)。
